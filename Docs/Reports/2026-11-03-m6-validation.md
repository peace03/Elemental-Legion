# M6 네트워크 부하 실행 및 검증

UDP 일반 서버와 플레이어가 여는 WSS 방에 봇 프로세스가 실제 게임 연결을 연다. 봇은 받은 위치와 관측 가능한 건물로 이동 방향을 정하고 서버 틱 주기로 명령을 전송한다. 정원 15명인 인터넷 방은 방장 봇 한 명과 참가자 봇 14명으로 채운다. HTTPS, WSS, 방 입장권, 준비, 시작과 복귀는 게임과 같은 경로를 통과한다.

## 반복 측정

전용 Linux 테스트 VM에 .NET 10 SDK, `iproute2`, OpenSSL과 `ethtool`이 필요하다. `tc netem`의 `seed` 옵션을 지원하는 커널과 `iproute2`를 사용한다. 저장소 루트에서 `sudo bash server/Tools/test-m6.sh`를 실행한다. `baseline`과 `netem`을 인수로 주면 각각 해당 반복만 실행한다. 두 경우 모두 접속과 복귀 검사부터 실행한다. [NetEm 원본 매뉴얼](https://github.com/iproute2/iproute2/blob/main/man/man8/tc-netem.8)

- 연결 확인은 UDP 1명, WSS 2명으로 수행한다. 복귀 확인에서는 15명이 움직인 뒤 마지막 참가자를 끊는다. 30초 안에 기존 플레이어 ID와 새로운 이동 적용 확인을 받고, 나머지 14명의 위치 틱도 계속 진행해야 한다.
- 15인 기본·지연 유실 조건을 각각 3회 실행한다. 매번 별도의 서버 저장소를 사용하고 시드 1, 워밍업 30초, 측정 300초를 적용한다. 참가자 전용 링크의 양방향에 각각 40ms 지연, ±10ms 지터, 1% 유실을 적용한다. 방장 프로세스와 중계는 같은 네임스페이스에 둔다. NetEm 설정과 실제 드롭 카운터를 실행 폴더에 보관한다.
- VM 안에서 만든 테스트 CA는 실행 프로세스의 `SSL_CERT_FILE`에만 지정한다. 호스트 이름 검증은 유지한다. 출력 경로는 `.artifacts/m6/linux.*`다. 모든 조건을 실행한 뒤 하나라도 실패하면 스크립트가 실패 코드를 반환한다.

## 다른 네트워크에서 실행

중계 PC에서 `Start-Server.cmd`의 **5번 인터넷 친구 테스트**를 실행하고 준비 완료 후 창을 켜 둔다. 다른 네트워크의 PC에서 같은 소스로 Release 빌드하고 아래 명령을 실행한다. 방 비밀번호는 도구가 생성한다.

```powershell
dotnet build server/ElementalLegion.sln -c Release -m:1 -nodeReuse:false
$relay = Read-Host '5번 실행기에 표시된 HTTPS 주소'
dotnet run --project server/Bots -c Release --no-build -- --bots 15 --relay $relay --host-server server/Server/bin/Release/net10.0/ElementalLegion.Server.dll --profile external --report .artifacts/m6/external.json
```

## 결과 판정

- `result.json`에는 프로토콜·게임 데이터 해시·측정 프로필·틱 범위, 실제 연결 수·유닛 수·공격 수, 봇별 명령과 바이트 수가 담긴다. 15명 유지, 예상 밖 연결 종료 0건, 서버 틱 p99가 20Hz에서 50ms 이하일 때 통과한다. 5분 부하에서는 측정 구간에 전투가 있어야 한다.
- `CommandResponse`로 접수를 확인하고, 해당 명령 순번에 도달한 첫 `Pose` 수신 시간으로 적용 지연을 계산한다. 제어 환경은 적용 지연 p95 250ms 이하가 기준이다. 미응답, 거절, 적용 확인 누락은 별도 건수로 남긴다. 외부망은 해당 회선에서 관측한 값을 별도로 기록한다.
- 서버 표본은 시뮬레이션, 복제 프레임 생성, 전송 큐 등록 시간을 포함한다. 애플리케이션 바이트는 전송 프로토콜 헤더와 재전송을 제외한다. 유닛 부하는 정상 시작 인구와 플레이 중 실제로 관측된 수로 해석한다. 표본 누락, 탈락, 성능 기준 초과가 있으면 실행 로그와 JSON을 보존하고 같은 조건으로 재현한다.

## 2026-11-03 Windows 로컬 결과

같은 Windows PC에서 Release 서버와 봇을 실행했다. 일부 UDP·WSS 실행은 겹쳤다. WSS는 실제 HTTPS 인증서 검증을 사용했고, 이 시험용 인증서와 개인 키는 종료 후 제거했다. 30초 워밍업 뒤 300초를 측정한 여섯 회차 모두 15명을 유지했다.

| 경로·회차 | 틱 p99 | 이동 적용 p95 | 플레이어 유닛 범위 | 공격 수 | 전송률 제한 거절 |
| --- | ---: | ---: | ---: | ---: | ---: |
| UDP 1 | 4.12ms | 108.03ms | 41–56 | 936 | 411 |
| UDP 2 | 3.99ms | 107.77ms | 41–53 | 873 | 334 |
| UDP 3 | 3.45ms | 107.82ms | 35–53 | 913 | 352 |
| WSS 1 | 4.22ms | 76.27ms | 26–35 | 667 | 266 |
| WSS 2 | 4.20ms | 74.71ms | 24–37 | 597 | 241 |
| WSS 3 | 3.83ms | 72.73ms | 22–35 | 609 | 240 |

모든 회차에서 틱 예산 초과, 예기치 않은 종료, 명령 미응답과 접수 후 적용 확인 누락이 0건이었다. 회차당 이동 명령은 약 9만 건이었다. UDP 1인·WSS 2인 접속 확인과 두 경로의 15인 복귀도 통과했다. 이전 실행의 틱 파일을 지정한 검사는 의도대로 실패를 반환했다. 원본 JSON과 틱 기록은 이 작업 공간의 `.artifacts/m6`에 있다.

.NET Release 빌드, 전체 테스트 241개, Unity 참조를 사용한 C# 컴파일과 Linux 스크립트의 Bash 문법 검사를 통과했다. **Linux NetEm 실측과 두 외부 네트워크를 사용하는 15인 측정은 남아 있다.**
