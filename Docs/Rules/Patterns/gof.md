# GoF 객체 지향 패턴 23개

생성·구조·행동의 객체 지향 패턴이다. 먼저 [선택 인덱스](../patterns.md)의 공통 기준을 적용하고, 현재 문제에 해당하는 분류만 읽는다.

## 생성 패턴: 무엇을 어떻게 만들 것인가

| 패턴 | 적용할 문제와 주의점 |
| --- | --- |
| Factory Method | 공통 생성 절차에서 구체적인 객체 종류를 구현별로 바꿔야 할 때 검토한다. 데이터 검증·의존성 연결이 반복되는 단순 생성은 일반 팩토리로 충분하며, 생성자 하나를 감싸려고 상속을 만들지 않는다. |
| Abstract Factory | 서로 호환되는 여러 객체를 한 묶음으로 교체해야 할 때 검토한다. 단일 객체 생성만 필요하면 사용하지 않는다. |
| Builder | 월드 초기화·테스트 준비처럼 여러 단계와 유효성 조건을 거쳐 복잡한 객체를 완성할 때 검토한다. 간단한 생성자까지 빌더로 바꾸지 않는다. |
| Prototype | 이미 구성된 객체를 복제해 변형할 때 검토한다. Unity의 프리팹 복제를 먼저 활용하고, 가변 컬렉션과 참조의 복사 범위를 명확히 한다. |
| Singleton | 프로세스 전체에서 하나여야 하는 자원에 한해 검토한다. 월드는 서버 안에 여러 개 존재할 수 있으므로 전역 단일 월드를 전제하지 않는다. 핵심 로직이 전역 접근에 의존하지 않게 한다. |

## 구조 패턴: 객체와 외부 기능을 어떻게 연결할 것인가

| 패턴 | 적용할 문제와 주의점 |
| --- | --- |
| Adapter | LiteNetLib·외부 에셋의 API를 프로젝트 인터페이스에 맞출 때 검토한다. 시뮬레이션에 외부 구현을 직접 노출하지 않는다. |
| Bridge | 추상 기능의 종류와 구현 방식이 서로 독립적으로 늘어날 때 검토한다. 단일 외부 API를 맞추는 문제라면 Adapter부터 검토한다. |
| Composite | UI·표현 요소처럼 개별 항목과 항목의 묶음을 같은 계약으로 다뤄야 할 때 검토한다. 군단이라는 이름만으로 모든 유닛을 트리 구조로 만들지 않는다. |
| Decorator | 같은 계약을 유지하면서 저장 압축·계측 등 부가 기능을 조합할 때 검토한다. 상태 효과의 중첩 규칙을 무분별한 래퍼 체인에 숨기지 않는다. |
| Facade | 여러 하위 시스템의 시작·종료 같은 사용 절차를 간단한 진입점으로 묶을 때 검토한다. 게임 로직 전체를 거대한 관리자에 몰아넣지 않는다. |
| Flyweight | 유닛별로 반복되는 불변 원소 정의 등을 공유해 메모리를 줄일 때 검토한다. 체력·위치·쿨타임 같은 개별 가변 상태는 공유하지 않는다. |
| Proxy | 실제 객체 접근 전에 지연 로딩·권한 확인 등을 처리할 때 검토한다. 서버 명령 검증을 대신하거나 중복하는 계층을 만들지 않는다. |

## 행동 패턴: 요청·상태·알고리즘을 어떻게 협력시킬 것인가

| 패턴 | 적용할 문제와 주의점 |
| --- | --- |
| Chain of Responsibility | 자원·해금·쿨타임 등 명령 검증 단계를 조합할 필요가 있을 때 검토한다. 검증 순서와 최초 실패 사유를 명확히 하고, 검증 중 상태를 일부 변경하지 않는다. |
| Command | 사람과 봇의 이동·건설·양성 요청을 같은 처리 경로로 전달한다. 명령에는 의도를 담고 서버가 검증한 뒤 상태를 변경한다. |
| Interpreter | 실제로 작은 규칙 언어의 해석이 필요할 때 검토한다. 현재 JSON 수치를 읽는 용도로 새 언어를 만들지 않는다. |
| Iterator | 자료구조의 내부를 노출하지 않고 순회해야 할 때 검토한다. 기존 컬렉션 순회 기능을 우선하고 반복 경로의 할당과 순서 재현성을 확인한다. |
| Mediator | UI 패널 등 여러 객체의 상호 호출이 복잡해질 때 협력을 조정한다. 모든 이벤트와 기능을 하나의 전역 중재자에 모으지 않는다. |
| Memento | 명시적인 상태 캡처·복원이 필요할 때 검토한다. 저장할 상태의 범위와 스키마·복사 비용을 정하며, 패턴만으로 영속 저장의 안전성이 보장된다고 보지 않는다. |
| Observer | 확정된 서버 결과를 UI·VFX·오디오에 알릴 때 사용한다. 구독·해제를 짝지으며, 핵심 판정 순서를 전역 이벤트 버스에 숨기지 않는다. |
| State | 접속·재접속·유령처럼 상태에 따라 동작과 전이가 달라질 때 검토한다. 배타적인 상태를 여러 bool 조합으로 표현하지 않는다. |
| Strategy | 특수 효과·표적 선택·봇 판단처럼 알고리즘이 달라지는 지점에 사용한다. 수치만 다르면 데이터로 처리한다. |
| Template Method | 여러 구현이 같은 처리 순서와 일부 다른 단계를 가질 때 검토한다. 공통 절차를 강제할 필요가 없다면 상속보다 조합을 우선한다. |
| Visitor | 객체 종류는 안정적이고 그 위에서 수행하는 연산이 자주 늘어날 때 검토한다. 원소 종류가 계속 늘어나는 문제에 무조건 적용하지 않는다. |
