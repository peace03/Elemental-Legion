# 최적화와 성능 검증

- 정확성과 재현성을 유지하면서 최적화한다. 우선 알고리즘과 자료구조를 검토하고, 복잡해지는 최적화는 병목 측정 후 적용한다.
- 매 틱·매 프레임·유닛별 반복 경로에서는 불필요한 GC 할당을 피한다. LINQ, 임시 컬렉션, 클로저, 박싱, 문자열 조합이 반복되는지 확인하고 버퍼를 재사용한다. 초기화·Editor 도구까지 일괄 금지하지 않는다.
- 적 탐색과 시야 조회는 공간 해시 등 범위를 줄이는 구조를 사용한다. 유닛 수에 따라 전체 쌍 비교가 늘어나는 구현을 기본 경로로 두지 않는다.
- Unity의 `GetComponent`, `Find*`, 리플렉션, 리소스 로딩은 필요한 시점에 실행하고 참조를 보관한다. 이를 `Update`나 유닛별 반복 처리에서 매번 수행하지 않는다.
- 파일 I/O, 동기 네트워크 대기, 대량 로그가 시뮬레이션 틱을 멈추지 않도록 한다. 외부 작업 결과를 월드에 적용하는 시점은 단일 스레드의 틱 경계로 모은다.
- Unity에서는 개체마다 독립적인 `Update`를 추가하기 전에 기존 갱신 경로를 활용할 수 있는지 확인한다. VFX의 입자 수, 오버드로, 드로 콜, 버퍼 크기와 풀 보유량도 성능 비용으로 관리한다.
- 성능 변경은 같은 시드·부하·실행 조건으로 전후를 비교한다. 서버는 평균·p99 틱 시간과 GC 할당, 클라이언트는 프레임 시간과 GC 할당, 네트워크는 클라이언트당 대역폭 등 변경과 관련된 지표를 보고한다.
- 측정하지 않은 성능 향상을 단정하지 않는다. 틱 예산은 `world.tickRate`에서 계산하며, 예산을 맞추려고 밸런스나 시야 차단을 임의로 바꾸지 않는다.
