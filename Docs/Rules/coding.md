# 코딩 규칙

이 문서는 공유 코드, 서버, 봇, 테스트, Unity 런타임 및 Editor 도구에 적용한다. 새 코드와 수정 범위에서 준수하며, 기존 코드 전체를 요청 없이 재작성하지 않는다. 외부 패키지·자동 생성 파일은 직접 고치지 않는다. 규칙을 적용할 수 없는 사유가 있으면 해당 위치와 이유, 대안을 작업 보고에 남긴다.

## SOLID와 책임 분리

SOLID는 변경이 다른 기능으로 번지지 않도록 책임과 의존성을 나누는 다섯 가지 원칙이다.

| 원칙 | 이 프로젝트에서 지킬 기준 |
| --- | --- |
| 단일 책임(SRP) | 클래스와 메서드는 하나의 역할에 집중한다. 입력 수신, 명령 검증, 시뮬레이션, 직렬화, 저장, Unity 표현을 한 클래스에 섞지 않는다. |
| 개방·폐쇄(OCP) | 일반적인 원소 추가와 수치 변경은 데이터로 처리한다. 실제로 다른 행동이 필요하면 기존 역할에 맞는 전략이나 처리기를 추가한다. 같은 분기가 여러 곳에 복제되지 않게 한다. |
| 리스코프 치환(LSP) | 구현을 교체해도 호출자가 기대하는 입력 조건, 결과, 오류 및 자원 소유권을 유지한다. 지원하지 않는 기능을 빈 메서드나 임의의 성공 값으로 감추지 않는다. |
| 인터페이스 분리(ISP) | 호출자가 필요한 기능만 갖는 작은 인터페이스를 사용한다. 읽기만 하는 코드에 상태 수정이나 저장 기능까지 의존시키지 않는다. |
| 의존성 역전(DIP) | 시뮬레이션은 Unity, 네트워크, 파일 시스템 같은 외부 구현을 직접 호출하지 않는다. 외부 경계는 필요한 인터페이스로 분리하고 시작 지점에서 연결한다. |

- 서버·공유 코드의 필수 의존성은 생성자로 전달한다. Unity 오브젝트 참조는 직렬화 필드나 명시적인 초기화 메서드로 연결하고, 사용 전에 누락을 확인한다.
- 인터페이스는 외부 경계나 실제 교체 지점에 둔다. 모든 클래스에 인터페이스·기반 클래스·팩토리를 기계적으로 만들지 않는다. 의존성 주입을 위해 새 프레임워크를 추가하지 않는다.
- 상속은 동일한 계약을 공유하는 관계에서만 사용한다. 기능 조합은 작은 객체나 Unity 컴포넌트의 조합을 우선한다.
- 전역 가변 상태, 서비스 로케이터, 어디서든 접근하는 Singleton에 핵심 로직을 의존시키지 않는다. 월드 상태와 난수의 소유자를 분명히 한다.

## 확장성과 데이터 관리

- 새 기능은 기존 호출자, 테스트, 데이터, 패킷, 씬·프리팹 연결까지 영향을 확인한 뒤 추가한다. 관련 없는 구조 변경을 섞지 않는다.
- 도메인 상태를 외부에서 임의로 변경하지 못하도록 캡슐화한다. 읽기 전용 조회와 검증을 거치는 변경 메서드를 구분하고, 컬렉션의 수정 권한도 제한한다.
- 문자열 ID, 메시지 종류, 데이터 키를 여러 파일에 복제하지 않는다. 프로젝트의 기존 정의를 재사용한다. 사람이 읽을 이름과 내부 ID는 구분한다.
- 실행 중 반복 사용하는 게임 데이터는 로딩 경계에서 검증하고 필요한 형태로 변환한다. 시뮬레이션 틱마다 JSON 파싱이나 문자열 경로 조회를 반복하지 않는다.
- 저장·패킷·Unity 직렬화 필드의 이름이나 형태를 바꾸면 기존 데이터와 참조가 유지되는지 확인한다. 필요하면 마이그레이션과 호환성 테스트를 함께 작성한다.
- 아직 요청하지 않은 기능을 위해 옵션, 플러그인 구조, 다단계 상속을 미리 만들지 않는다. 현재 요구를 완성하는 가장 작은 구조를 선택한다.

## 디자인 패턴 적용 기준

- 특정 목록으로 사용 가능한 패턴을 제한하지 않는다. GoF뿐 아니라 EventBus, MVC·MVP·MVVM, 아키텍처·게임·저장·메시징·비동기·네트워크 패턴과 기법도 문제에 맞게 적극 검토한다.
- 선택이 필요한 작업에서는 [디자인 패턴 상세 문서](patterns.md)의 관련 분류를 읽는다. 예시는 선택을 돕는 기준이며 전부 구현해야 하는 목록이 아니다.
- 기존 구현과 패턴을 먼저 재사용하고, 단순한 데이터·함수·조건문과 비교해 변경 범위와 복잡도를 줄이는 방식을 선택한다. 채택 이유가 구조에서 드러나지 않으면 한글 주석으로 설명한다.
- 패턴 적용 후에도 서버 권위, 상태 변경 시점, 틱 순서, 자원 소유권을 추적할 수 있어야 한다. 작은 작업을 패턴 이름에 맞추려고 여러 클래스로 늘리지 않는다.

## 읽기 쉬운 코드와 한글 주석

- 타입·멤버·변수는 역할을 설명하는 영문 이름을 사용하고, 직접 작성하는 설명 주석·XML 문서·인스펙터 설명은 한글로 쓴다. API 이름, 원소 ID, 단위 등 정확한 식별자는 유지한다.
- C# 기본 명명 규칙을 따른다. 타입·메서드·프로퍼티는 `PascalCase`, 매개변수·지역 변수·private 필드는 `camelCase`, 인터페이스는 `I` 접두사를 사용한다. 수정하는 파일에 일관된 기존 규칙이 있으면 불필요한 이름 변경을 피한다.
- 각 클래스에는 책임을 설명하는 짧은 한글 요약을 둔다. 외부에서 호출하는 주요 API에는 입력 단위, 반환 의미, 상태 변경이나 호출 순서의 제약 중 이름만으로 알기 어려운 내용을 설명한다.
- 복잡한 계산, 좌표 변환, 양자화, 서버 검증, 해시 정규화에는 이유와 경계 조건을 설명한다. 코드와 함께 주석도 수정한다.
- 모든 줄을 그대로 번역하는 주석, 의미 없는 getter 설명, 실제 동작과 다른 주석은 쓰지 않는다. 메서드가 길고 여러 역할이 섞이면 주석으로 구획만 나누지 말고 역할별로 정리한다.
- 깊은 중첩보다 명확한 조건 검사와 조기 반환을 사용한다. 정상 흐름과 실패 처리를 구분하며, 의미가 불분명한 숫자·불리언 인수를 반복해서 넘기지 않는다.
- 게임 수치는 JSON에서 읽는다. 프로토콜 크기나 비트 마스크 같은 기술 상수는 이름을 붙여 정의하고, 게임 밸런스와 구분한다.

## 검증, 오류 처리와 수명 관리

- 클라이언트 패킷, 데이터 파일, 저장 파일은 신뢰 경계에서 검증한다. 길이·범위·ID·빈 값과 함께 좌표 등의 `NaN`·무한대도 확인한다. 잘못된 입력이 월드 상태를 일부만 변경하지 않게 한다.
- 예측 가능한 명령 거절은 정의된 결과나 사유 코드로 처리한다. 예외를 정상적인 유닛별 반복 흐름에 사용하지 않는다.
- 예외를 빈 `catch`로 무시하거나 실패를 성공으로 바꾸지 않는다. 복구할 수 없는 초기화·데이터 오류는 원인이 드러나게 실패시키며, 로그에는 작업 대상과 원인을 남긴다. 비밀값과 불필요한 개인정보는 기록하지 않는다.
- 파일 저장은 기존 정상 데이터를 먼저 지우지 않는다. 임시 파일에 저장하고 검증 후 교체하는 등 실패 시 원본을 보존할 수 있는 방식을 사용한다.
- 소켓·스트림·이벤트 구독·코루틴·비동기 작업의 소유자와 종료 시점을 정한다. 오브젝트 비활성화·파괴·접속 종료 시 정리하고, 취소된 작업이 늦게 상태를 변경하지 않도록 한다.
- `async void`는 API가 요구하는 이벤트 처리기 외에는 사용하지 않는다. 비동기 작업의 예외와 취소를 호출자가 관찰할 수 있게 한다.
