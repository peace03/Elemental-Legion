# 포트폴리오를 위한 게임 개발일지 템플릿

작업 하나나 기술 결정 하나를 단위로 아래 **복사용 양식**을 복제한다. 평소에는 **목표 → 구현 → 결과 → 근거**를 짧게 남긴다. 판단을 바꾼 문제나 실험이 있었으면, 그때의 재현 조건과 선택 근거도 남긴다.

포트폴리오로 옮길 때는 한 가지 기술적 판단을 중심으로 편집한다. **첫 화면**에는 바뀐 동작이 드러나는 제목, 내 역할과 결과, 대표 자료 하나를 둔다. **본문**에는 어떤 제약에서 무엇을 관찰했고 왜 그 구현을 선택했는지 적는다. **하단**에는 원본 로그·코드·재현 방법을 둔다. 이 순서면 훑어보는 독자도 내 작업을 파악하고, 자세히 보는 독자는 판단의 근거까지 따라갈 수 있다.

## 말투와 편집 기준

- **행동이 드러나는 문장으로 쓴다.** “동기화 품질을 개선했다”보다 “서버 위치가 도착하면 서버가 아직 적용하지 않은 이동 입력만 다시 계산했다”처럼 쓴다. 팀 결과는 팀의 주어로 쓰고, 직접 설계·구현·검증한 동작에는 내가 한 일을 드러낸다. 기여율을 추정하기보다 담당 범위를 구체적으로 적는다.
- **사고 흐름은 관찰이 다음 행동을 바꾼 지점으로 보여준다.** “여러 방법을 시도했다”보다 “밀집 표본에서 탐색·오라 구간이 오래 걸렸다. 전체 탐색과 같은 표적을 고르면서 조사할 칸 수를 줄이기로 했다”가 판단을 설명한다. 작업의 모든 순서를 나열할 필요는 없다.
- **사실, 해석, 계획을 문장으로 구분한다.** “경계 앞 정지를 재현했다”는 확인한 사실이다. “제보한 위치도 본진 경계였을 가능성이 있다”는 해석이다. “다음에는 서버 좌표와 입력 번호를 남긴다”는 계획이다. 검토하지 않은 대안이나 실패를 회고에 보태지 않는다.
- **제목과 첫 문단만 읽어도 변화가 보여야 한다.** “M0 최적화 작업”보다 “988기 밀집 교전에서 서버 틱 p99 14.149ms → 5.013ms”가 대상과 결과를 말해 준다. p99나 클래스 이름은 쓰는 이유가 있을 때만 짧게 풀어 설명한다. 상세 로그와 긴 코드 전문은 링크로 뺀다.

## 이미지와 영상은 설명할 주장에 맞춰 고른다

| 독자가 확인할 내용 | 어울리는 자료 | 캡션에 적을 내용 |
| --- | --- | --- |
| 입력에 따라 동작이 바뀐다 | 입력부터 결과까지 보이는 짧은 영상·GIF | 조작, 관찰할 위치, 결과가 나오는 시점. 링크 영상이라면 해당 타임스탬프 |
| 버그나 아트 문제가 개선됐다 | 전후 스크린샷이나 같은 장면을 나란히 놓은 영상 | 같은 카메라·장면·입력으로 비교하고, 달라진 곳만 번호나 테두리로 표시 |
| 구현에서 책임과 데이터가 나뉜다 | 작은 흐름도 또는 핵심 코드 링크 | 입력·판정·출력의 방향, 서버·클라이언트 경계, 내가 수정한 지점 |
| 성능 또는 검증 결과가 달라졌다 | 전후 수치 표, 프로파일러 구간, 테스트 로그 | 단위, 표본 조건, 개선 기준, 확인한 항목과 제외한 비용 |

- 대표 자료는 요약 바로 아래, 원인 확인용 자료는 관련 문단 옆에 둔다. 그림마다 보여줄 주장 하나를 정하고, 영상은 첫 장면에 볼 대상을 표시한다. 두 플레이어 화면이라면 A/B와 각 시야의 관측 대상을 글자로 표기한다.
- 캡션은 **볼 위치 → 보이는 변화 → 확인 조건** 순으로 한두 문장을 쓴다. 본문 폭에서 글자와 지표를 읽을 수 있는지 확인한다. 자료에 대체 텍스트를 달고, 확대본과 원본은 링크로 남긴다.
- 자료가 보여주는 범위만 주장한다. 렌더 표본은 그 장면의 표현을, UDP 로그는 수신한 정보의 범위를 보여준다. 재현용 테스트 장면, 실제 Play, Windows Player, 합성·주석한 이미지는 캡션에서 구분한다.

### 작성자가 필요한 자료를 직접 만들고 검수한다

- 일지를 쓰는 사람이 설명에 필요한 자료를 선택해 제작하고 본문에 배치한다. 실제 캡처가 있으면 먼저 활용하고, 구조는 도식으로, 측정 결과는 원본 데이터에 따른 그래프로 만든다. 자료 제작에는 별도의 요청을 기다리지 않는다.
- 도식에는 입력·판정·출력의 방향과 담당 주체를 표시한다. 그래프에는 단위·실험 조건·원본 출처를 붙인다. 과거 작업을 정리할 때는 당시 커밋과 보고서를 사용하고, 이후 구현이나 측정을 섞지 않는다.
- 새로 그린 자료에는 구조 설명도·측정 기록 재구성 등 제작 성격을 캡션으로 밝힌다. 실행 화면과 성능 수치는 확인한 자료를 사용한다. 생성한 목업을 실제 플레이 캡처나 측정 증거로 제시하지 않는다.
- 모바일에서는 가로로 긴 그림을 한꺼번에 축소하기보다 세로 흐름이나 작은 단위로 나눈다. 핵심 설명은 이미지 밖의 텍스트로도 남기고, 확대 안내와 원본 링크를 제공한다. 파일명과 수정 가능한 원본도 기록한다.
- Notion에 올린 뒤 실제 페이지를 PC 폭과 모바일 폭에서 열어 이미지 글자·문단 밀도·줄바꿈·표의 넘침을 확인한다. 작은 글자와 긴 문단은 수정 후 다시 본다. 검수한 폭과 스크린샷을 남기고, 모바일 폭 검수와 실제 스마트폰 앱 검수는 구분해 보고한다.

## 작성 예시 · Elemental Legion의 밀집 전투 측정

- **목표와 문제** · 유닛이 한곳에 몰렸을 때 서버 시뮬레이션의 틱 시간 p99가 10ms 이하여야 했다. 플레이어 유닛 750기와 중립 238기를 배치한 첫 밀집 측정에서는 p99가 14.149ms였다.
- **선택과 해결** · 현재 격자 칸부터 표적을 찾고, 더 가까운 후보가 나올 수 없는 칸을 거리 하한으로 건너뛰었다. 반복 버퍼를 미리 확보하고 진형 정렬의 불필요한 객체 변환도 없앴다. 전체 탐색과 결과를 비교하는 경계 테스트를 추가했다.
- **결과와 범위** · i5-12400F의 M0 Release 측정에서 밀집 p99가 14.149ms → 5.013ms로 줄었고 공격·사망·전향 집계는 유지됐다. 고정 시드 1, 워밍업 1,000틱, 측정 10,000틱 조건이다. UDP 전송과 Unity 렌더링은 이 수치에서 제외됐다. [M0 검증 기록](Reports/2026-11-02-m0-validation.md)
- **후속 아이디어 예시** · 새 시야·전투 결과 기능을 붙인 빌드에서 같은 부하를 재현하고, 표적 탐색·시야 계산·패킷 작성 시간을 따로 측정해 다음 개선 대상을 고른다.

이 캡처를 본문 폭에 놓으면 중앙 전투가 작게 보인다. 방벽과 체력 표현을 설명하는 글이라면 중앙을 확대해 해당 유닛을 표시하고 원본을 링크한다. 전향 전후를 보여주려면 소유자 표시가 바뀌는 구간의 영상이 필요하다. 화면 한 장으로 두 클라이언트의 정보 분리나 프레임 성능을 설명하려면 근거가 부족하므로, 그 주장에는 별도의 UDP 로그나 측정 표를 붙인다. [교전 영상 원본](Reports/M3/combat.avi) · [UDP 테스트 원문](Reports/M3/dotnet-tests.txt)
